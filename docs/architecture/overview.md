## 외부 의존성

| 서비스 | 용도 | 현재 사용 한도 | 무료 한도 | 상태 |
|--------|------|---------------|----------|------|
| **Clerk** | 사용자 인증 (이메일+Google) | < 10명 | 10K MAU | ✓ |
| **Neon** | PostgreSQL 데이터 (users, search_logs, api_keys) | < 1MB | 0.5GB | ✓ |
| **Upstash Redis** | 검색 캐시 (TTL 7일) | < 100 keys | 10K req/일, 256MB | ✓ |
| **우리말샘 API** | 사전 데이터 원천 (바다 키 1개) | < 100 호출/일 | 5만 호출/일 | ✓ |
| **Vercel** | SaaS 호스팅 + 서버리스 함수 | 미배포 | 무료 (개인) | 🔜 Phase 7 |

→ **모든 서비스 무료 티어로 1년 운영 가능**. 비용 0원.

## 핵심 설계 원칙

### 1. 모든 검색은 SaaS를 거친다
로컬 HUD가 우리말샘을 직접 호출하지 않음. 이유:
- **API 키 보호**: 우리말샘 키는 SaaS 서버에만 보관
- **공유 캐시**: 한 명이 검색하면 모두에게 즉시 응답
- **사용 통계**: 사용자별 패턴 수집 → 1년 후 유료화 협상 자료
- **유료화 lock**: 구독 안 한 사용자 차단 가능 (Phase 8 예정)

### 2. JIT(Just-In-Time) 사용자 등록
Clerk webhook 대신, 사용자가 페이지 진입 시 우리 DB에 row 자동 생성:
- 외부 webhook 등록 없이 로컬 개발에서도 정상 동작
- webhook 자체는 코드로 작성됨 → Phase 7 배포 후 활성화 (선택)

### 3. 두 가지 인증 방식 공존
- **Clerk 쿠키**: 브라우저 SaaS 사용자
- **API 키 (Bearer)**: 로컬 HUD 사용자

`/api/search`는 둘 다 받음 (Authorization 헤더 있으면 Bearer, 없으면 Clerk).

### 4. status 검사로 보호 라우트 구현
`(dashboard)` 라우트 그룹의 layout이 자동으로:
- 비로그인 → `/sign-in`
- status≠approved → `/pending`

API 라우트도 동일 검사 (외부 도구로 우회 불가).

## 데이터 흐름 요약

상세는 [data-flow.md](data-flow.md). 큰 흐름만:

1. **회원가입**: 사용자 → Clerk(가입) → SaaS 페이지 진입 → JIT으로 DB row(`status='pending'`) 생성 → `/pending` 페이지로
2. **승인**: 관리자가 Neon SQL 또는 `/admin/users`(Phase 5)에서 `status='approved'`로 변경
3. **API 키 발급**: 사용자가 `/api-keys` → 평문 1회 노출, DB는 SHA256 해시
4. **검색** (브라우저): `/search` → `/api/search` → Redis 조회 → (miss면) 우리말샘 → 캐시 → `search_logs`
5. **검색** (로컬 HUD): F2/F3 단축키 → IPC → `dictionary-api.ts` → SaaS `/api/search` (Bearer) → 위와 같은 흐름 → HUD 결과 표시
